# ARC-001 — Утвердить целевую архитектуру и dependency rules

- Статус: DONE (принято координатором 2026-09-05)
- Владелец: Claude
- Scope: часть 1 — `eslint.config.js` (инструментальные границы). Часть 2 (продолжение,
  описанная ниже) — перемещение файлов внутри `src/core/**` и `src/application/**` под целевое
  дерево из плана §4, без изменения публичного API. Ни одна часть не трогает файлы, над которыми
  сейчас работает art-агент (`arena-decoration.ts`, `prototype-scene.ts`,
  `dream-environment-manifest.ts`).

## Часть 1 — инструментальные архитектурные границы (ESLint boundaries)

- Изменённые файлы: `eslint.config.js`.
- Что реализовано:
  - `no-restricted-imports` для `src/core/**`: запрет на `phaser`, `react`, `react-dom`,
    `@capacitor/*`, `@adapters/*`, `@ui/*`, `@content/*`, `@application/*`.
  - `no-restricted-globals` для `src/core/**`: запрет на `window`/`document`/`localStorage`.
  - `no-restricted-imports` для `src/application/**`: запрет на `phaser`/`react`/`react-dom`/
    `@capacitor/*`/`@adapters/*`/`@ui/*`.
  - `no-restricted-imports` для `src/content/**`: запрет на `phaser`/`@capacitor/*`/`@adapters/*`/
    `@ui/*`/`@application/*` — content остаётся декларативным.
  - `no-restricted-imports` для `src/adapters/**`: запрет на `@ui/*`.
  - `no-restricted-properties` для всего `src/**`, кроме `src/adapters/storage/**` и
    `src/ui/App.tsx` (composition root, только передаёт `Storage`-ссылку, не читает/пишет через
    неё): запрет на `window.localStorage`.
- Что намеренно не реализовано: отдельный пакет `eslint-plugin-boundaries` не добавлялся — все
  правила выражены встроенными ESLint-правилами (`no-restricted-imports`/`no-restricted-globals`/
  `no-restricted-properties`), это не требует новой зависимости и покрывает те же случаи для
  текущего масштаба проекта.
- Известные ограничения: правила основаны на встроенных ESLint-механизмах, а не на выделенном
  плагине границ — при значительном росте числа слоёв (например появлении `ui/bridge` как
  отдельного пакета) может понадобиться `eslint-plugin-boundaries` для более выразительных
  правил (glob-to-glob запреты одним объявлением).

## Часть 2 (продолжение) — целевая структура каталогов core/application

- Изменённые файлы (все — `git mv`, история сохранена):
  - `src/core/gameplay/*` → распределено по
    `src/core/{combat,abilities,entities,events,phase,puzzle}/*` и двум файлам верхнего уровня
    `src/core/models.ts`, `src/core/game-session.ts` (обоснование ниже).
  - `src/core/state/*` → `src/core/state-machine/*` (переименование каталога под точное имя из
    целевого дерева плана §4).
  - `src/application/{app-controller,gameplay-controller,progress-service}.ts` →
    `src/application/services/*`.
  - Обновлены барели: `src/core/index.ts`, `src/core/state-machine/index.ts` (новый, заменил
    `src/core/state/index.ts`), `src/application/index.ts`. Старый `src/core/gameplay/index.ts`
    удалён.
  - Точечные правки относительных импортов внутри перемещённых файлов
    (`combat/combat-rules.ts`, `events/game-event.ts`, `phase/phase-cycle.ts`,
    `game-session.ts`, `save/save-game.ts`, `application/services/progress-service.ts`).
- Что реализовано:
  - `src/core/combat/` — `bond-health.ts`, `combat-rules.ts`.
  - `src/core/abilities/` — `cooldown-tracker.ts`, `eclipse-meter.ts`.
  - `src/core/entities/` — `enemy-ai-profile.ts`.
  - `src/core/events/` — `game-event.ts`.
  - `src/core/phase/` — `phase-cycle.ts`, `boss-phase-tracker.ts`.
  - `src/core/save/` — не менялось, уже совпадало с планом.
  - `src/core/state-machine/` — `app-state.ts`, `app-state-machine.ts` (было `core/state/`).
  - `src/application/services/` — `app-controller.ts`, `gameplay-controller.ts`,
    `progress-service.ts`.
  - `src/application/ports/` — не менялось, уже совпадало с планом.
- Что намеренно не реализовано (с обоснованием):
  - **`src/core/models.ts` и `src/core/game-session.ts` оставлены на верхнем уровне `core/`, а не
    засунуты в одну из восьми подпапок целевого дерева.** `models.ts` — сквозной набор доменных
    типов (`CatId`, `Phase`, `AbilityConfig`, `EnemyConfig`, `HeroProgress`, `GameplaySnapshot` и
    т.д.), которые одновременно нужны `combat`, `abilities`, `entities`, `events`, `phase` —
    распределение по этим папкам создало бы циклические импорты между ними или потребовало бы
    произвольного выбора «главного» владельца типа. `game-session.ts` — единственный класс,
    который _компонует_ `BondHealth`+`CooldownTracker`+`EclipseMeter`+`PhaseCycle`+combat-rules,
    т.е. он не принадлежит ни одной из подпапок по определению (это корень агрегата). План прямо
    разрешает такое решение: «Структура уточняется после аудита текущего репозитория. Не
    переносить файлы механически ради соответствия дереву: каждое перемещение должно иметь цель и
    проходящие проверки» (§4). Насильно раскладывать эти два файла по подпапкам создало бы
    искусственную фрагментацию без реальной пользы и с риском циклов импорта.
  - **`src/core/puzzle/` — новая подпапка, отсутствующая в буквальном списке целевого дерева
    плана.** `sequence-puzzle.ts` (генерический class для проверки последовательности активаций,
    используемый механикой рун сада) не относится ни к combat, ни к abilities, ни к phase, ни к
    progression (в смысле HeroProgress/unlocks) — это самостоятельная примитивная механика. Так
    как план прямо разрешает уточнять структуру, добавлена одна точечная папка вместо
    искусственного впихивания в несвязанную категорию.
  - **`application/commands`/`application/queries` не создавались** — `AppController` и
    `GameplayController` смешивают команды и запросы в одном классе каждый; формальное разделение
    методов на отдельные `commands`/`queries` — это поведенческий рефакторинг класса, а не
    перемещение файла (уточнение уже существующего `ARC-006`, event/command bridge). Смешивать
    его с перемещением файлов нарушило бы принцип «низкий риск, механическое перемещение».
  - **`content/characters/` не создавалась** — это `content`, не `core`/`application`, не
    относится к этой задаче.
- Известные ограничения: `application/services/` сейчас содержит и контроллеры (Phaser↔React
  bridge), и progress-service — по своей природе это разные роли (bridge vs. use-case service),
  сгруппированные вместе только потому, что план не выделяет отдельную папку для controllers.
  Если формальное разделение `commands`/`queries` когда-либо будет сделано, вероятно потребуется
  ещё одно перемещение файлов внутри `application/`.

## Общее для обеих частей

- Изменённые контракты: **нет изменений публичного API.** Все внешние потребители продолжают
  импортировать через `@core/index` / `@application/index`; единственное исключение —
  `src/adapters/storage/local-storage-save-repository.ts`, которое импортирует
  `@application/ports/save-repository` напрямую — путь порта не менялся, поэтому это тоже не
  затронуто.
- Проверки и результаты:
  - `npm run lint` — 0 нарушений (граница уже соблюдалась де-факто до части 1, теперь закреплена
    инструментально; правила из части 1 автоматически применились и к новым путям части 2, так
    как используют glob `src/core/**`/`src/application/**`, а не конкретные файлы).
  - `npm run typecheck` — чисто.
  - `npm run test` — 14 файлов / 35 тестов, все проходят без изменений в тестах (тесты
    импортируют только через `@core/index`/`@application/index`/`@content/index`, внутреннее
    перемещение файлов их не затронуло).
  - `npm run build` — production build проходит.
  - `npm run format:check` — чисто для всех тронутых файлов (два предсуществующих warning на
    `AGENTS.md`/`docs/ECLIPSE_PAWS_SCENARIO.md` не относятся к этой задаче).
- Ручная проверка: не требуется — конфигурационное изменение (часть 1) и чисто структурный
  рефакторинг без изменения поведения (часть 2), оба подтверждены полным набором тестов и
  production build.
- Скриншоты/видео: не применимо.
- Риски для следующих задач: любой новый файл в `src/core`, `src/application` или `src/content`,
  который случайно импортирует Phaser/React/DOM/соседний слой, теперь будет падать на
  `npm run lint` — это ожидаемое поведение, а не регрессия. `ARC-010` (Destroyable/scene lifecycle
  contract, cleanup для Phaser-систем) не пересекается с этим перемещением — `prototype-scene.ts`
  и другие adapters импортируют core/application только через неизменившиеся барели, но `ARC-010`
  всё равно трогает `prototype-scene.ts`, который сейчас правит art-агент — синхронизировать перед
  стартом.
- Рекомендованный следующий task ID: дождаться сигнала от пользователя о завершении работы
  art-агента над декорациями, затем `ARC-010` (Destroyable-контракт для Phaser-систем в
  `prototype-scene.ts`).
