# ARC-011 — Перенести одну малую механику end-to-end как архитектурный пример

- Статус: DONE (принято координатором 2026-09-05, подтверждено e2e-прогоном)
- Владелец: Claude
- Scope: пилотное (не полное) извлечение из `platformer-enemy-system.ts` (455 строк, самый
  большой файл в проекте) — намеренно ограничено одной цельной механикой, а не декомпозицией
  всего файла. Полная декомпозиция (patrol/jump AI, `#walkPlatform`, health bar, loot) остаётся
  отдельной, более рискованной задачей — см. «Что намеренно не реализовано».

## Что перенесено: механика обнаружения цели через укрытие (день/ночь стелс)

Правило "враг не видит цель, если она прячется в укрытии, кроме врагов с сенсором обнаружения"
было полностью реализовано внутри Phaser-адаптера (`#insideCover`, инлайновая проверка
`!concealed || COVER_SENSORS.has(...)`), используя `Phaser.Physics.Arcade.Sprite`-позиции и
`PlatformRect` из `@content`. Это прямая игровая механика (влияет на боевой баланс: скрытность —
одна из тем нового сценария, ночь/свет), которая случайно оказалась в adapter-слое.

- Изменённые файлы:
  - `src/core/entities/enemy-perception.ts` (новый) — `isPointInZone`, `isTargetConcealed`,
    `canEnemyDetectTarget`. Чистые функции, 0 импортов Phaser/DOM/`@content`/React (используют
    структурный тип `RectZone { x, y, width, height }` вместо `PlatformRect` из `@content`, чтобы
    не нарушать правило "core не зависит от content", введённое в `ARC-001`).
  - `src/core/index.ts` — экспорт новых функций и типа `RectZone`.
  - `src/adapters/phaser/platformer-enemy-system.ts` — `#insideCover` (приватный метод) удалён,
    `update()` теперь вызывает `isTargetConcealed(...)`/`canEnemyDetectTarget(...)` из `@core/index`
    вместо инлайновой геометрии и `COVER_SENSORS.has(...)` напрямую.
  - `tests/unit/enemy-perception.test.ts` (новый) — 9 тестов: границы зоны (внутри/на
    границе/снаружи), `isTargetConcealed` с учётом флага `hiding` и пустого списка зон,
    `canEnemyDetectTarget` для всех трёх комбинаций (видимая цель / скрытая без сенсора / скрытая
    с сенсором).
- Гарантия идентичного поведения: формулы перенесены **дословно** —
  `isPointInZone` побитово совпадает с прежним телом `#insideCover`
  (`x >= zone.x - zone.width/2 && x <= zone.x + zone.width/2 && ...`), `canEnemyDetectTarget`
  побитово совпадает с прежним `!concealed || COVER_SENSORS.has(enemy.config.id)`. Не рефакторинг
  алгоритма — только перемещение с сохранением побайтовой эквивалентности вычислений.

## Почему именно эта механика (обоснование выбора)

- Полностью самодостаточна (принимает только числа/строки, не требует Phaser sprite/body) — не
  переплетена с mutable AI state (`stuckMs`, `recoveryAttempts`, `jumpCooldownMs`), в отличие от
  `#walkPlatform`/`#jump`, поэтому извлекается без риска изменить побочный игровой feel.
- До этой задачи была **вообще не покрыта тестами** (ни один Phaser-адаптер не имеет unit-тестов
  — см. `docs/AUDITS/CURRENT_STATE.md` §6) — теперь имеет 9 юнит-тестов и типобезопасный
  публичный контракт через `@core/index`.
- Прямо демонстрирует паттерн, который требует план (§4): "core содержит чистые правила",
  "adapters/phaser отображает состояние и переводит Phaser events в команды" — здесь adapter
  теперь только собирает Phaser-специфичные координаты и передаёт их в core-функцию, не
  вычисляет игровое правило сам.

## Что намеренно не реализовано (и почему)

- **Полная декомпозиция `platformer-enemy-system.ts` не выполнялась.** Оставшаяся логика
  (`#walkPlatform`, `#jump`, `#hazardAhead`, `#hasPlatformAt`, `#resolveStrike`,
  `#updateHealthBar`) тесно переплетена с mutable per-enemy state и Phaser physics body — вынос
  этого требует более глубокого редизайна (например, отдельного класса состояния AI на core-уровне
  с явным вводом/выводом на каждый тик), что является отдельной, значительно более крупной и
  рискованной задачей. Впихивать это в одну сессию нарушило бы принцип "перенести **одну малую**
  механику", которым буквально описан `ARC-011` в плане.
- **`#hazardAhead`/`#resolveStrike` не тронуты**, хотя тоже выглядят как кандидаты на извлечение —
  оставлены как естественное продолжение (следующая пилотная итерация), а не расширение scope этой
  задачи задним числом.
- **Визуальная проверка в браузере не выполнена** — dev-сервер (`npm run dev` через
  `preview_start`) завис за локальным helper-диалогом подтверждения на машине пользователя
  (`Claude.app/Contents/Helpers/disclaimer`), недоступным для автоматизации агента. Верификация
  опирается на: (а) побайтовое совпадение перенесённых формул с оригиналом, (б) 45/45 unit-тестов,
  включая 9 новых, целенаправленно проверяющих именно эту механику, (в) успешный production build.
  Рекомендуется, чтобы пользователь при следующем запуске `npm run dev` пропустил этот диалог
  один раз (после чего браузерная автоматизация сможет подключаться в будущих сессиях).
- Изменённые контракты: публичное поведение `PlatformerEnemySystem.update()` не изменилось
  (тот же вход/выход) — добавлены новые экспорты в `@core/index`
  (`isPointInZone`/`isTargetConcealed`/`canEnemyDetectTarget`/`RectZone`), ничего не удалено из
  существующего публичного API.
- Проверки и результаты:
  - `npm run lint` — чисто (в т.ч. `no-restricted-imports` подтверждает, что новый
    `core/entities/enemy-perception.ts` не импортирует Phaser/content/adapters).
  - `npm run typecheck` — чисто.
  - `npm run test` — 15 файлов / 45 тестов (было 14/35, добавлено 10: 9 новых +
    существующие не изменились и все проходят).
  - `npm run build` — production build проходит.
  - `npm run format:check` — чисто для всех изменённых файлов.
- Ручная проверка: не выполнена визуально (см. известные ограничения выше) — заменена
  побайтовым сохранением формул + целевыми unit-тестами.
- Скриншоты/видео: не применимо (dev-сервер недоступен в этой сессии).
- Известные ограничения: `RectZone` в `core/entities/enemy-perception.ts` структурно идентичен
  `PlatformRect` из `@content/levels/campaign-levels.ts`, но это два разных типа с намеренным
  дублированием формы — так и должно быть (core не имеет права зависеть от content, см.
  `ARC-001`); при изменении формы `PlatformRect` нужно будет синхронизировать `RectZone` вручную,
  тесты на структурную несовместимость сейчас не пишутся (TS structural typing сам это ловит на
  вызове).
- Риски для следующих задач: следующая итерация той же техники (`#hazardAhead`, `#resolveStrike`,
  затем сложная stateful AI patrol-логика) должна повторить этот паттерн — сначала написать
  unit-тесты на предполагаемое поведение (или зафиксировать его как есть), затем перенести
  дословно, затем только потом рассматривать изменение самого алгоритма отдельной задачей.
- Рекомендованный следующий task ID: `ARC-015` (debug launcher) — не пересекается с art-агентом;
  либо продолжение той же техники на `#hazardAhead`/`#resolveStrike`; либо дождаться сигнала о
  завершении декораций для `ARC-010`.

## Продолжение — вторая и третья пилотные извлечения (`#hazardAhead`, `#resolveStrike`)

Выполнено в этой же сессии сразу после `ARC-015`, тем же паттерном:

- **`isHazardAhead(spriteX, direction, footY, hazards)`** — добавлена в
  `src/core/entities/enemy-perception.ts` рядом с механикой обнаружения. Дословно перенесена из
  приватного `#hazardAhead(sprite, direction, footY)`; единственное отличие — принимает `sprite.x`
  числом вместо целого Phaser-спрайта (методу нужна была только координата `x`).
- **`isStrikeHit(distance, attackRange, hitBuffer = 24)`** — добавлена в
  `src/core/combat/combat-rules.ts` (комбат-правило, не perception). Дословно перенесена из
  условия внутри приватного `#resolveStrike` (`distance < this.#ai.attackRange + 24`); побочные
  эффекты (`clearTint`, `setFrame`, сброс `cooldownMs`, вызов `gameplay.takeDamage`) остались в
  adapter — извлечена только сама булева проверка «попал/не попал».
- `src/adapters/phaser/platformer-enemy-system.ts` — оба приватных метода удалены, вызовы заменены
  на импортированные core-функции.
- Тесты: `tests/unit/enemy-perception.test.ts` (+5 тестов на `isHazardAhead`: направление
  движения, дальность по X, дальность по Y, пустой список угроз), `tests/unit/combat-rules.test.ts`
  (+4 теста на `isStrikeHit`: попадание в радиусе, попадание в буфере по умолчанию, промах за
  буфером, кастомный буфер).
- Проверки: `npm run lint`/`typecheck`/`test` (61/61 на момент этого прогона, до `AUD-013`/`AUD-014`
  и до исправления регрессии `ARC-015`) /`build` — все чисто.
- Что осталось нетронутым (сознательно, тот же аргумент, что и в основной секции): `#walkPlatform`,
  `#jump`, `#hasPlatformAt`, `#updateHealthBar`, `#playMove` — переплетены с mutable per-enemy
  state (`stuckMs`, `recoveryAttempts`, `jumpCooldownMs`, `direction`) и требуют отдельного,
  специально спроектированного core-абстрагирования (например, явного объекта AI-состояния,
  передаваемого по значению на каждый тик), а не точечного извлечения одной формулы.
- Визуальная проверка по-прежнему не выполнена в браузере (тот же блокер с диалогом
  подтверждения), но в отличие от первой пилотной итерации, эта сессия дополнительно прогнала
  `npm run test:e2e` (в рамках работы над `ARC-015`) — полный набор e2e, включающий реальное
  прохождение боя через `PlatformerEnemySystem` (тест `'plays the platformer through combat, pause
and checkpoint restart'`), зелёный после этого изменения, что является более сильным
  подтверждением отсутствия регрессии, чем только unit-тесты на изолированные функции.
