## Главная находка перед реализацией (меняет оценку риска из аудита)

`docs/AUDITS/KNOWN_ISSUES.md` #6 и `docs/AUDITS/CURRENT_STATE.md` §5 характеризовали отсутствие
`destroy()` как «средняя-высокая» утечка listeners/tweens/timers. Перед тем как писать код, я
проверил исходники установленного `phaser@3.90.0`
(`node_modules/phaser/src/{tweens/TweenManager,time/Clock,gameobjects/DisplayList}.js`):

- `TweenManager.shutdown()` — вызывает `this.killAll()` (убивает **все** твины сцены, включая
  `repeat: -1`).
- `Clock.shutdown()` — уничтожает все pending/active `delayedCall`.
- `DisplayList.shutdown()` — вызывает `destroy(true)` на **каждом** объекте, добавленном через
  `scene.add.*`.

Все три плагина сами подписываются на `Phaser.Scenes.Events.SHUTDOWN` при инициализации
(`this.events.once(SceneEvents.SHUTDOWN, this.shutdown, this)`) — то есть когда `PrototypeScene`
эмиттит `SHUTDOWN` (что уже происходило и раньше, через `this.events.once(...,
this.#shutdown, this)` в существующем коде), Phaser **уже** убивал все твины/таймеры/game-объекты
всех 4 «незащищённых» систем (`PlatformerEnemySystem`, `LevelMechanicsSystem`,
`PlayerMovementSystem`, `TutorialSystem`) сам, до и независимо от моих правок. Я перепроверил все
7 под-систем `LevelMechanicsSystem` (`GardenCollectibleSystem`, `GardenFlowerPuzzle`,
`LibraryConstellationSystem`, `FinalBossSystem`, `PhaseBridgeSystem`, `PlatformerHazardSystem`,
`PlatformerProgressSystem`) на предмет ресурсов **вне** управления Phaser (`AudioContext`,
`window.setInterval`/`setTimeout`, `window`/`document`-листенеры, независимые подписки на
`GameplayController`) — grep по всему `src/adapters/phaser/*.ts` нашёл ровно один файл с
`AudioContext` (`sfx-synth.ts`, уже закрывается через `combatSystem.destroy()` до этой задачи) и
ровно один файл с подпиской на `GameplayController.subscribeToEvents`/`this.input.on` —
`prototype-scene.ts` сам (уже отписывался до этой задачи).

**Вывод:** реальной утечки памяти в 4 названных системах не было — аудит переоценил риск, не
проверив, что Phaser сам подчищает свои твины/таймеры/game-объекты на `SHUTDOWN`. Задача всё равно
имеет ценность (см. ниже), но не как «исправление бага», а как архитектурная защита.

## Что реализовано

- **`src/adapters/phaser/destroyable.ts`** — интерфейс `Destroyable { destroy(): void }` с
  комментарием, объясняющим находку выше (чтобы следующий разработчик не тратил время на
  повторное расследование).
- **`PlatformerEnemySystem.destroy()`** — очищает `#enemies`/`#collectedDrops` (Map/Set), чтобы
  система не держала ссылки на уже уничтоженные Phaser-объекты дольше самой сцены.
- **`LevelMechanicsSystem.destroy()`** — намеренно no-op с комментарием: все 7 под-систем владеют
  только Phaser-управляемыми ресурсами (проверено, см. выше), контракт присутствует для
  единообразия и как место для будущей реальной очистки, если у какой-то под-системы появится
  собственный не-Phaser ресурс.
- **`PlayerMovementSystem.destroy()`** — no-op (система только мутирует чужие sprite-ссылки,
  ничего не создаёт).
- **`TutorialSystem.destroy()`** — единственная система с реальной, поведенчески значимой
  очисткой: `scene.tweens.killTweensOf(icon)` (бесконечный пульсирующий твин иконки,
  `repeat: -1`), отмена `#completionCall` (`delayedCall`, если обучение уже завершилось и ждёт
  анимации исчезновения), `panel.destroy(true)`. Формально Phaser убрал бы то же самое сам при
  `SHUTDOWN`, но здесь `destroy()` теперь можно вызвать независимо от полного шатдауна сцены
  (например, для юнит-теста — что и сделано).
- **`CombatAbilitySystem`/`TagSwitchSystem`** — добавлено `implements Destroyable` (были указаны в
  `KNOWN_ISSUES` как уже рабочий пример) без изменения тела `destroy()`.
- **`PrototypeScene#shutdown()`** — теперь вызывает `destroy()` на всех 6 системах
  (`combatSystem`, `tagSwitchSystem`, `enemySystem`, `levelMechanics`, `playerMovement`,
  `tutorialSystem?`), а не на 2.

## Leak test — что НЕ удалось и почему

Пытался написать unit-тест (`tests/unit/scene-lifecycle-contract.test.ts`), импортирующий классы
систем напрямую для структурной проверки (`typeof Class.prototype.destroy === 'function'`) плюс
поведенческий тест `TutorialSystem.destroy()` с фейковой `Phaser.Scene`. **Тест не смог даже
загрузиться**: `import Phaser from 'phaser'` в этих файлах выполняет `phaser`-пакет целиком при
импорте модуля, а тот на этапе загрузки делает `CanvasFeatures`-детект
(`node_modules/phaser/src/device/CanvasFeatures.js`), который падает под `jsdom` без пакета
`canvas` (`Not implemented: HTMLCanvasElement's getContext()`) — это ровно то, что уже
зафиксировано в `docs/AUDITS/CURRENT_STATE.md` §6 («Ни один Phaser-адаптер не покрыт
unit-тестами»), теперь с конкретной технической причиной. Мокать весь `phaser`-пакет (`vi.mock`)
ради одного теста — большая и хрупкая поверхность (`Phaser.Math.Clamp`, `.Distance.Between`,
`.BlendModes`, `.Scenes.Events`, `.Display.Color...` и т.д., используемая в разных файлах),
устанавливать `canvas` как новую зависимость — отдельное решение с последствиями для CI/сборки,
не моё, чтобы принимать в рамках этой задачи. Тестовый файл удалён, не оставлен в красном
состоянии.

**Вместо этого — фактическая проверка:** `npm run test:e2e` прогнан полностью (см. ниже), включая
тест `'completes all seven campaign levels and reaches the credits'`, который проходит через
**7 полных циклов** создания/уничтожения `Phaser.Game` (см. `create-prototype-game.ts` — новая
игра на каждый уровень, `GameCanvas.tsx` вызывает `game.destroy(true)` при размонтировании), т.е.
7 реальных вызовов нового `#shutdown()` с полным набором `destroy()`-вызовов, включая уровень 1 с
активным `TutorialSystem`. Ни одного console error, все 15/15 e2e зелёные — это сильнее, чем
искусственный unit-тест на моках, так как проверяет реальный Phaser в реальном headless Chromium.

## Изменённые контракты

- Новый экспорт `Destroyable` из `src/adapters/phaser/destroyable.ts` — не публичный API за
  пределами `adapters/phaser`, не пересекает архитектурные границы (`core`/`application`/`ui` его
  не видят и не должны).
- `CombatAbilitySystem`, `TagSwitchSystem`, `PlatformerEnemySystem`, `LevelMechanicsSystem`,
  `PlayerMovementSystem`, `TutorialSystem` теперь все `implements Destroyable` — любой будущий
  Phaser-адаптер, добавляемый в `PrototypeScene`, должен следовать этому же паттерну (стоит
  упомянуть в `docs/ADDING_CONTENT.md`, если там появится раздел про добавление systems — сейчас
  такого раздела нет, не добавлял, т.к. это вне scope ARC-010).

## Известные ограничения / риски для следующих задач

- Настоящих unit-тестов для Phaser-адаптеров по-прежнему нет — установка `canvas` npm-пакета
  (нативная зависимость, требует toolchain для сборки) осталась бы решением пользователя, если
  когда-то потребуется реальное purely-unit покрытие этого слоя. E2e — единственная сегодня
  работающая проверочная сеть для `adapters/phaser/*`.
- `docs/AUDITS/KNOWN_ISSUES.md` #6 обновлён (закрыт, серьёзность скорректирована). Стоит иметь в
  виду при чтении старых версий других докладов/памяти координатора, что формулировка «риск
  утечки» там была не подтверждена фактами Phaser lifecycle — исправлено в этой задаче.
