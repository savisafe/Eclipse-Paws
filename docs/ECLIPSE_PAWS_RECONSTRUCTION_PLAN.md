# Eclipse Paws — мастер-план реконструкции

> Главный исполняемый план для поэтапной реконструкции существующей игры несколькими агентами.
>
> Каждый агент обязан прочитать этот файл и `ECLIPSE_PAWS_SCENARIO.md` целиком до начала работы. Агент выполняет только назначенные ему задачи, не меняет канон самостоятельно и передаёт результат координатору через формализованный handoff.

## 1. Цель реконструкции

Перестроить существующую браузерную игру в законченную детскую 2D/2.5D action-platformer **Eclipse Paws** из семи уровней:

- сохранить работоспособные части текущей реализации;
- заменить старую историю новой историей Элиаса, Лумуса и Нокса;
- превратить однотипные платформы и пропасти в уникальные живые локации;
- добавить постепенное развитие способностей;
- реализовать комиксный пролог и эпилог;
- обеспечить понятное управление двумя котами;
- сделать архитектуру расширяемой и пригодной для web, iOS и Android;
- сохранить стабильную playable-версию после каждого этапа;
- довести проект до состояния, в котором новый уровень, персонаж или способность добавляются через предсказуемый production-процесс.

Реконструкция выполняется **инкрементально**, без единовременного переписывания всей игры.

## 2. Источники истины и приоритет документов

При конфликте решений использовать следующий порядок приоритета:

1. `ECLIPSE_PAWS_SCENARIO.md` — сюжет, персонажи, семь уровней, эмоциональная дуга и способности.
2. `ECLIPSE_PAWS_RECONSTRUCTION_PLAN.md` — этапы работ, статусы, владельцы, архитектурные и production-требования.
3. `docs/DECISIONS.md` — утверждённые технические решения и исключения.
4. `docs/GAME_DESIGN.md` — числовой баланс и актуальные игровые правила.
5. `docs/ART_BIBLE.md` — визуальный язык, размеры, палитры, экспорт и анимации.
6. `docs/LEVELS/LEVEL_N.md` — карта, сцены, расстановка и параметры конкретного уровня.
7. `README.md` — команды запуска и общее описание проекта.
8. Старый технический или сюжетный документ — только как историческая справка.

Координатор обязан пометить устаревшие документы и не позволять агентам восстанавливать выведенные из канона решения: Небесный Маятник, пять осколков, Сумеречник, Кокс и Боня как игровые имена.

## 3. Неподвижные продуктовые решения

- Главные герои: белый кот Лумус и чёрный кот Нокс; оба мальчики.
- Их хозяин — древний волшебник Элиас.
- Игра начинается и заканчивается комиксным слайд-шоу.
- В игре семь уровней.
- Шестой уровень посвящён Арену, погибшему брату Элиаса.
- Игра рассчитана на детей, но имеет второй смысл для взрослых.
- Свет не равен добру, а тьма не равна злу.
- Днём ведущим бойцом является Лумус, ночью — Нокс.
- Ночь является настоящим ограничением видимости и изменением мира, а не цветовым фильтром.
- Противники — фантастические защитные конструкции сна, а не реальные люди или животные.
- Элиас не уничтожает Безмолвие; он принимает его как часть себя.
- Финал не обещает волшебного исцеления от утраты.
- Каждый уровень имеет уникальный рельеф, декорации, интерактивные объекты и характер перемещения.
- Gameplay core не зависит от React, DOM, Phaser и Capacitor.

Изменение любого пункта требует решения пользователя и записи в `docs/DECISIONS.md`.

## 4. Целевая техническая основа

### Стек

- TypeScript в strict-режиме;
- Vite;
- Phaser 3 — сцены, камера, ввод, физика, анимации, частицы и звук;
- React — меню, HUD, диалоги, настройки и экраны глав;
- Zustand — только UI/session state;
- Vitest — unit и integration tests;
- Playwright — smoke/e2e;
- ESLint и Prettier;
- Capacitor — мобильная оболочка после стабилизации web-версии.

Перед обновлением зависимостей агент проверяет совместимость, фиксирует версию lock-файлом и не выполняет массовый upgrade вместе с gameplay-задачей.

### Целевая структура

```text

    combat/
    entities/
    events/

    progression/
    save/
    state-machine/

      entities/
      physics/
      camera/
      animation/
      audio/
      effects/
    input/
    storage/
    haptics/

    abilities/
    enemies/
    characters/
    dialogue/
    levels/

    hud/
    menus/
    dialogue/

```

Структура уточняется после аудита текущего репозитория. Не переносить файлы механически ради соответствия дереву: каждое перемещение должно иметь цель и проходящие проверки.

### Архитектурные границы

- `core` содержит чистые правила и не импортирует Phaser, React, DOM API или Capacitor.
- `application` координирует use cases и зависит от портов, а не от конкретных адаптеров.
- `adapters/phaser` отображает состояние и переводит Phaser events в команды приложения.
- `ui` общается с игрой через типизированный bridge, не хранит gameplay state.
- `content` содержит проверяемые конфигурации, а не произвольную логику сцен.
- доступ к `localStorage` разрешён только реализации `SaveRepository`.
- все входные устройства преобразуются в абстрактные `GameAction`.
- расчёты механик используют фиксированный simulation step.
- случайность, влияющая на тесты и encounters, использует injectable seeded RNG.
- загрузка и выгрузка сцен обязаны очищать listeners, timers, tweens, audio и physics bodies.
- ошибки content-конфигураций выявляются при сборке или загрузке уровня с понятным сообщением.

## 5. Организация многоагентной работы

### Роли

| Роль | Ответственность | Не изменяет без согласования |
|---|---|---|
| Координатор / Lead | План, декомпозиция, зависимости, интеграция, статусы | Канон и продуктовые решения |
| Architecture Agent | Core, application, ports, adapters, lifecycle | Сюжет, визуальный стиль, баланс |
| Gameplay Agent | Movement, abilities, combat, companions, phase | UI вне игрового bridge, финальный арт |
| Level Design Agent | Blockout, ритм, маршруты, encounters, checkpoints | Core API без ADR |
| Narrative Agent | Диалоги, comic beats, environmental storytelling | Механики и архитектуру |
| Art Agent | Concept, sprites, backgrounds, props, atlases | Collision и gameplay rules |
| Animation/VFX Agent | State animations, transitions, readability | Damage и timings без Gameplay Agent |
| UI/UX Agent | HUD, меню, onboarding, mobile controls | Gameplay state ownership |
| Audio Agent | Music, SFX, ambience, audio cues | Сюжетные реплики без Narrative Agent |
| QA/Accessibility Agent | Tests, matrices, regression, accessibility | Фичи вне отдельного bug task |
| Performance/Build Agent | Profiling, bundles, mobile constraints, CI | Gameplay feel без согласования |

Один агент может выполнять несколько ролей последовательно, но не смешивает несвязанные задачи в одном изменении.

### Идентификаторы задач

- `AUD-NNN` — аудит;
- `ARC-NNN` — архитектура;
- `GAM-NNN` — общие механики;
- `ABL-NNN` — способности;
- `ART-NNN` — арт и анимации;
- `COM-NNN` — комиксные сцены;
- `UIX-NNN` — UI/UX;
- `LV1-NNN` … `LV7-NNN` — конкретные уровни;
- `NAR-NNN` — текст и повествование;
- `AUDI-NNN` — звук;
- `ACC-NNN` — доступность;
- `QAT-NNN` — тестирование;
- `PRF-NNN` — производительность;
- `MOB-NNN` — мобильная упаковка;
- `REL-NNN` — релиз.

Каждый commit, handoff и статус содержит ID задачи.

### Единственный владелец статусов

Только координатор изменяет:

- чекбоксы и статусы в этом файле;
- общую task board;
- порядок фаз;
- статус milestone/gate.

Исполняющие агенты не редактируют мастер-план параллельно. Они создают отчёт `docs/HANDOFFS/TASK_ID.md`, после чего координатор проверяет работу и обновляет статус. Это предотвращает конфликты в главном документе.

### Статусы

- `BACKLOG` — задача описана, но не готова к старту;
- `READY` — входные данные и зависимости готовы;
- `IN_PROGRESS` — назначен один владелец;
- `REVIEW` — реализация и handoff готовы;
- `BLOCKED` — есть конкретный блокер;
- `DONE` — координатор принял задачу и проверки прошли;
- `DEFERRED` — осознанно перенесено, указана причина.

### Правила параллельной работы

- одновременно не редактировать один файл без заранее разделённых участков;
- не переключать общую git-ветку во время работы другого агента;
- для настоящего параллелизма использовать отдельные `git worktree` или изолированные рабочие копии;
- если worktree недоступны, выполнять пересекающиеся задачи последовательно;
- один агент владеет task ID от начала до handoff;
- изменение публичного интерфейса требует уведомить всех потребителей в handoff;
- контракт сначала фиксируется типами и тестами, затем меняются реализации;
- интеграцию нескольких веток выполняет только координатор;
- запрещено исправлять «заодно» несвязанные проблемы без отдельного task ID;
- обнаруженный дефект записывается отдельной задачей, если не блокирует текущую.

### Definition of Ready

Перед назначением задачи проверяется:

- [ ] указан task ID и владелец;
- [ ] описан пользовательский результат;
- [ ] известны входные файлы и допустимая область изменений;
- [ ] перечислены зависимости;
- [ ] приложены сценарный фрагмент, layout или contract;
- [ ] определены проверки и acceptance criteria;
- [ ] нет другого агента, меняющего те же файлы;
- [ ] нет неразрешённого продуктового решения.

### Handoff исполнителя

Файл `docs/HANDOFFS/TASK_ID.md` содержит:

```markdown
# TASK_ID — короткое название

- Статус: REVIEW
- Владелец:
- Scope:
- Изменённые файлы:
- Что реализовано:
- Что намеренно не реализовано:
- Изменённые контракты:
- Проверки и результаты:
- Ручная проверка:
- Скриншоты/видео:
- Известные ограничения:
- Риски для следующих задач:
- Рекомендованный следующий task ID:
```

### Definition of Done

- [ ] acceptance criteria выполнены;
- [ ] изменение ограничено назначенным scope;
- [ ] `lint` проходит;
- [ ] `typecheck` проходит;
- [ ] unit/integration tests проходят;
- [ ] production build проходит;
- [ ] применимые e2e проходят;
- [ ] нет новых console errors;
- [ ] добавлены или обновлены тесты;
- [ ] обновлена применимая документация;
- [ ] проверены desktop и mobile viewport;
- [ ] проверено освобождение ресурсов сцены;
- [ ] проверено сохранение/загрузка, если затронут прогресс;
- [ ] приложены визуальные доказательства для UI/level/art задач;
- [ ] handoff заполнен;
- [ ] координатор провёл review и отметил задачу `DONE`.

## 6. Production-пайплайн уровня

Ни один уровень не переходит сразу от сценария к финальной графике.

### Шаг 1 — Level brief

- сюжетная функция;
- новые и проверяемые способности;
- основной landmark;
- тип рельефа и движения;
- день/ночь и их влияние;
- три обязательных взаимодействия;
- противники и encounter roles;
- NPC и сюжетные сцены;
- точки отдыха;
- секреты и награды;
- бюджет ассетов и производительности.

### Шаг 2 — Beat map

На одной схеме обозначить:

- старт и завершение;
- последовательность эмоциональных и gameplay-битов;
- безопасное обучение;
- первое применение под давлением;
- развилки и места соединения маршрутов;
- checkpoints;
- арены;
- диалоги;
- панорамы;
- comic transition.

### Шаг 3 — Graybox

- только простая геометрия и placeholder-объекты;
- зафиксированы размеры котов, скорость, прыжок и камера;
- проверены подъёмы, спуски, slopes и landing zones;
- нет final art;
- уровень можно пройти от начала до конца;
- измерены время прохождения и частота переключения котов;
- устранены soft locks.

### Шаг 4 — Gameplay pass

- способности работают во всех предусмотренных контекстах;
- companion AI проходит маршрут;
- day/night изменяет геометрию и восприятие;
- расставлены интерактивы, враги, NPC и checkpoints;
- encounter difficulty соответствует уровню;
- подсказки появляются поэтапно;
- секреты не блокируют основной сюжет.

### Шаг 5 — Art pass

- утверждён paint-over graybox;
- платформенная геометрия замаскирована тематическим рельефом;
- foreground не закрывает опасности;
- фон имеет ограниченный parallax и не мешает читаемости;
- landmark видим из ключевых точек;
- collision остаётся стабильной после замены ассетов;
- интерактивные объекты отличимы формой и анимацией.

### Шаг 6 — Lighting, VFX и audio pass

- день и ночь имеют разные источники света, ambience и частицы;
- настоящая ночь остаётся играбельной при разных настройках экрана;
- атаки и опасности читаются до декоративных эффектов;
- звуки помогают ориентироваться за пределами видимости;
- отсутствуют резкие вспышки без accessibility-настройки;
- одновременно активные частицы ограничены budget.

### Шаг 7 — Polish и lock

- gameplay, visual, narrative, accessibility и performance reviews;
- playtest минимум с одним игроком, не знающим решение;
- исправлены критические проблемы навигации;
- записано эталонное прохождение;
- после level lock изменения выполняются только отдельными задачами.

### Чек-лист расстановки каждой зоны

- [ ] следующая цель или landmark видны либо понятно подсказаны;
- [ ] основной маршрут читается по форме рельефа без стрелки поверх экрана;
- [ ] есть безопасное место первого знакомства с новой механикой;
- [ ] интерактивные объекты отличаются от обычного декора формой и анимацией;
- [ ] опасности имеют telegraph и не появляются внутри игрока;
- [ ] NPC не стоят в зоне случайного урона;
- [ ] перед важным диалогом есть спокойная площадка;
- [ ] после сложного участка есть передышка;
- [ ] checkpoint находится до сложной комбинации;
- [ ] секрет подсказан визуально, но не блокирует основной маршрут;
- [ ] камера показывает место приземления и источник угрозы;
- [ ] foreground не закрывает героев, края и telegraphs;
- [ ] ночная версия проходима по контурам, звукам и landmark;
- [ ] spawn points имеют стабильные ID;
- [ ] day/night variants используют один логический объект, если это одна сущность;
- [ ] переход назад не приводит к soft lock или повторному сюжетному trigger;
- [ ] companion имеет navigation markers/wait points;
- [ ] зона проверена с минимальными декоративными эффектами.

## 7. Art- и animation-пайплайн

### Обязательные документы

- `docs/ART_BIBLE.md` — формы, контур, материалы, палитры, свет и допустимая мрачность;
- `docs/CHARACTER_SHEETS.md` — пропорции и turnaround;
- `docs/ANIMATION_LIST.md` — состояния и приоритеты;
- `docs/ASSET_MANIFEST.md` — ID, владелец, статус, размеры, формат, лицензия;
- `docs/COMIC_STORYBOARD.md` — 8 кадров пролога и 8 кадров эпилога;
- `docs/LEVELS/LEVEL_N_ART.md` — список фонов, tiles, props, NPC и VFX уровня.

### Статусы ассета

`BRIEF → SKETCH → REVIEW → APPROVED → PRODUCTION → INTEGRATED → VERIFIED → LOCKED`

Файл не считается готовым на статусе `APPROVED`: его нужно встроить, проверить в движении и подтвердить на целевых viewport.

### Именование

```text
category_character_action_variant_frame.ext
chr_lumus_run_day_01.png
chr_nox_ability_spikes_night_06.png
npc_gardener_idle_day_03.png
env_l01_sunflower_open_02.png
bg_l02_canopy_far_day.webp
vfx_eclipse_ring_01.png
comic_prologue_panel_01.webp
```

- только латиница, lowercase и snake_case;
- стабильный semantic ID не зависит от имени файла;
- day/night variant указан явно;
- временные файлы имеют суффикс `_temp` и не попадают в release manifest;
- источник, лицензия и автор фиксируются в manifest;
- сгенерированный AI-арт не считается финальным без art review и проверки прав использования.

### Персонажи и анимации

Для Лумуса и Нокса нужны:

- turnaround и silhouette test;
- idle, blink, look, groom;
- walk, run, start, stop, turn;
- jump rise, apex, fall, land;
- slope up/down;
- interact, push, pull;
- hurt, recover, defeat;
- phase weaken/empower;
- отдельная анимация каждой способности;
- совместное Затмение;
- comic/emote poses;
- переходы, чтобы действия не обрывались между состояниями.

Для Элиаса нужны возрастные варианты: ребёнок, молодой ученик, взрослый и древний волшебник. Все варианты должны сохранять узнаваемые черты и один повторяющийся символ.

Для каждого NPC и противника сначала утверждаются silhouette, role и telegraph. Декоративная детализация добавляется после проверки читаемости на игровом масштабе.

### Технический экспорт

- базовое разрешение и pixels-per-unit фиксируются до массовой отрисовки;
- тестировать на design viewport 1280×720 и минимальном mobile viewport;
- прозрачные sprites — lossless PNG/WebP с alpha;
- фон без alpha — WebP с проверенным качеством;
- atlases группируются по уровню и частоте использования;
- mobile atlas не превышает безопасный texture size целевых устройств;
- trim, padding и extrusion единообразны, чтобы избежать texture bleeding;
- исходники хранятся отдельно от runtime-экспорта;
- импорт выполняется скриптом, а не ручным копированием;
- manifest проверяет отсутствующие, дублирующиеся и неиспользуемые ассеты;
- loading screen показывает реальный прогресс загрузки.

### Чек-лист готовности ассета

- [ ] соответствует `ART_BIBLE.md`;
- [ ] имеет стабильный semantic ID и владельца;
- [ ] исходник сохранён отдельно от runtime-файла;
- [ ] имя соответствует convention;
- [ ] формат и размеры соответствуют manifest;
- [ ] pivot/origin не прыгает между кадрами;
- [ ] hitbox не повторяет мелкие детали рисунка;
- [ ] проверен на дневном и ночном фоне;
- [ ] читается в минимальном мобильном масштабе;
- [ ] не сливается с декором и опасностями;
- [ ] добавлен в manifest и правильный atlas;
- [ ] отсутствуют texture bleeding и дрожание;
- [ ] day/night variants добавлены, если нужны;
- [ ] лицензия/происхождение зафиксированы;
- [ ] проверен внутри игры, а не только отдельно;
- [ ] performance budget подтверждён;
- [ ] временный ассет удалён или явно помечен.

## 8. Общие технические задачи

### Movement и камера

- [ ] единые метрики скорости, ускорения, прыжка и гравитации;
- [ ] jump buffer;
- [ ] coyote time;
- [ ] регулируемая высота прыжка;
- [ ] корректная физика slopes;
- [ ] предсказуемые moving platforms;
- [ ] защита от застревания на краях;
- [ ] камера с look-ahead и мягким vertical follow;
- [ ] камера показывает landing zone;
- [ ] camera bounds задаются конфигурацией уровня;
- [ ] screen shake имеет лимит и reduced-motion режим;
- [ ] respawn не запускает повторно просмотренные диалоги.

### Companion system

- [ ] второй кот следует без постоянного микроконтроля;
- [ ] избегает известных опасностей;
- [ ] умеет ждать на парной точке;
- [ ] не ломает moving platforms и elevators;
- [ ] догоняет через безопасный warp вне поля зрения;
- [ ] имеет понятный индикатор, если временно разделён с игроком;
- [ ] переключение active cat не меняет направление случайно;
- [ ] общая шкала связи синхронизирована с HUD;
- [ ] companion tests покрывают типовые layouts всех уровней.

### Day/night и настоящая ночь

- [ ] состояние фазы принадлежит core;
- [ ] уровень описывает phase-specific objects декларативно;
- [ ] ночь использует light mask/visibility system, а не fullscreen overlay;
- [ ] область видимости Нокса имеет мягкую границу;
- [ ] Лумус остаётся заметен ночью, не раскрывая всю сцену;
- [ ] navigation cues видимы формой, контуром и звуком;
- [ ] интерактивные объекты меняют поведение, а не только tint;
- [ ] UI не затемняется сценой;
- [ ] яркость ночи регулируется;
- [ ] transitions очищают временные объекты и не дублируют listeners;
- [ ] screenshot tests сравнивают day/night readability.

### Ability system

- [ ] единый interface/config для ability;
- [ ] unlocks хранятся в progression state;
- [ ] cooldown, cost и cast phases не зависят от scene FPS;
- [ ] hit detection отделён от animation;
- [ ] targeting одинаково работает с keyboard, gamepad и touch;
- [ ] отмена/прерывание способности имеет явные правила;
- [ ] VFX и SFX запускаются событиями, а не содержат правила урона;
- [ ] способности имеют combat и environment use;
- [ ] каждый unlock сопровождается безопасной тренировкой;
- [ ] старые сохранения получают корректную миграцию unlocks.

### Save и progression

- [ ] `SaveGame` имеет `schemaVersion`;
- [ ] хранится последний завершённый уровень, checkpoints, unlocks, collectibles и settings;
- [ ] повреждённое сохранение восстанавливается безопасно;
- [ ] миграция старого сохранения протестирована;
- [ ] chapter select не ломает progression;
- [ ] replay уровня не удаляет дальнейший прогресс;
- [ ] cutscenes можно повторно открыть;
- [ ] storage доступен через port;
- [ ] подготовлены web и будущий native adapter.

## 11. Контроль scope и риски

| Риск | Ранний сигнал | Мера |
|---|---|---|
| Big-bang rewrite | неделями нет playable build | вертикальные миграционные срезы и feature flags |
| Art bottleneck | graybox ждёт финальные sprites | placeholders, manifest и asset contracts |
| Однотипные уровни | меняются только фон и tint | уникальные movement/interaction budgets |
| Перегрузка способностями | растёт число кнопок | максимум 3 действия, upgrades/context |
| Нечитаемая ночь | игрок повышает яркость монитора | light mask, outlines, audio cues, brightness setting |
| Companion ломает платформинг | частые падения второго кота | assist AI, wait points, safe warp, route tests |
| Рассинхронизация агентов | конфликтующие контракты | один owner, handoff, coordinator-only integration |
| Scope creep семи уровней | незавершённый первый slice | level gates и запрет mass art до Gate 5 |
| Слишком мрачная подача | дети не хотят продолжать | символы, юмор, передышки, child playtests |
| Слишком буквальная мораль | длинные объясняющие монологи | environmental storytelling и короткие реплики |
| Mobile memory failure | context loss/reloads | atlases по уровню, unload, budgets, device tests |
| Потеря сохранений | schema меняется без migration | versioned save и fixtures каждой версии |

## 12. Playtesting gates

Рекомендуемый временной бюджет первого прохождения ребёнком:

- уровни 1–2: 15–20 минут каждый;
- уровни 3–5: 20–30 минут каждый;
- уровни 6–7: 25–35 минут каждый.

Это гипотеза для тестирования, а не норматив. Слишком короткий уровень можно расширять только содержательными сценами и взаимодействиями, а не повторными боями или длинными переходами.

### Graybox gate

- [ ] пять новых игроков прошли обязательный маршрут без указаний разработчика;
- [ ] минимум четыре из пяти поняли главную цель;
- [ ] минимум четыре из пяти самостоятельно применили новую способность после обучения;
- [ ] никто не оставался без решения более трёх минут до появления помощи;
- [ ] все случайные падения и ложные маршруты записаны;
- [ ] измерено время каждой зоны;
- [ ] отмечены места, где игроки перестают переключать котов;
- [ ] уровень остаётся понятен без финального декора.

### Content alpha gate

- [ ] уровень проверили минимум три ребёнка целевой возрастной группы с согласия взрослых;
- [ ] уровень проверили минимум три взрослых;
- [ ] наблюдатель не направлял игрока во время прохождения;
- [ ] после прохождения игрок своими словами объяснил цель, новую способность и смысл главной сцены;
- [ ] обязательный маршрут завершили минимум 80% участников;
- [ ] отдельно записаны выходы, поражения, пропуски и неверные трактовки;
- [ ] исправлены все blocker и места массового непонимания;
- [ ] эмоционально тяжёлая сцена проверена на понятность и безопасность.

### Release playtest gate

- [ ] полная игра пройдена каждым поддерживаемым способом управления;
- [ ] игра пройдена в стандартном и упрощённом режимах;
- [ ] сохранение переживает закрытие приложения на переходах;
- [ ] пролог, эпилог и главы доступны повторно;
- [ ] финальная мысль понятна ребёнку без объяснения взрослого;
- [ ] финал не воспринимается как обещание, что любовь полностью устраняет горе;
- [ ] отсутствуют места обязательного grind;
- [ ] ни одно поражение не отнимает больше 60–120 секунд прогресса;
- [ ] повтор encounter занимает не более пяти секунд после загрузки.

### Локальные playtest-метрики

Если команда добавляет телеметрию, она работает локально, выключается пользователем и не содержит имён, текста диалогов, IP или других персональных данных.

Допустимые события: начало/завершение уровня, checkpoint, показ подсказки, использование способности, смена фазы, поражение с категорией причины, пропуск слайд-шоу и изменение accessibility-настройки.

- [ ] схема событий версионирована;
- [ ] журнал ограничен кольцевым буфером;
- [ ] журнал можно удалить и экспортировать в JSON;
- [ ] debug-события исключены из production;
- [ ] сбор локальных метрик не является условием прохождения;
- [ ] любое внешнее отправление данных требует отдельного решения пользователя и privacy review.
