# ARC-014 — Content и save-game validation через Zod

> Переименовано из первоначального черновика `ARC-002.md`: этот task ID случайно совпал с уже
> существующим пунктом Фазы 1 плана (`ARC-002` = «настроить strict TypeScript, lint, format и
> typecheck», который был выполнен ещё до этой сессии). Работа, описанная ниже, фактически
> соответствует `ARC-014` («Добавить runtime-валидацию content schemas, например Zod») и попутно
> закрывает `ARC-009` («Добавить content schema validation») — обе задачи из Фазы 1 плана.

- Статус: DONE (принято координатором 2026-09-05)
- Владелец: Claude
- Scope: `src/core/save/*`, новый `src/content/schema.ts`, подключение валидации в
  `src/content/levels/campaign-levels.ts`, `package.json`/`package-lock.json` (добавлен прямой
  devDependency→dependency `zod`, ранее присутствовал только транзитивно через
  `eslint-plugin-react-hooks`).
- Изменённые файлы:
  - `package.json`, `package-lock.json` — `zod@^4.5.4` как прямая зависимость.
  - `src/core/save/save-game.schema.ts` (новый) — Zod-схемы `SaveGame`/`SavedSettings`/
    `HeroProgress`, отдельно для текущей версии схемы и legacy-миграции.
  - `src/core/save/save-game.ts` — `parseSaveGame`/`migrateSave` переведены с ручных
    `typeof`/`Array.isArray` проверок на `schema.safeParse`, поведение и порядок приоритетов полей
    сохранены один в один.
  - `src/content/schema.ts` (новый) — структурные Zod-схемы `AbilityConfig`/`EnemyConfig`/
    `CampaignLevelDefinition` и `validateCampaignContent()`, которая дополнительно проверяет
    ссылочную целостность: что каждый `enemy.configId` в уровне существует в `enemyTypes`, и что
    `bossId` резолвится либо в `enemyTypes`, либо в список enemy spawn id уровня.
  - `src/content/levels/campaign-levels.ts` — вызов `validateCampaignContent(...)` на реальных
    `PROTOTYPE_ABILITIES`/`*_ENEMIES`/`CAMPAIGN_LEVELS` сразу после их определения (fail fast при
    импорте модуля).
  - `tests/unit/save-game.test.ts` — добавлен тест на отклонение `SaveGame` с некорректными
    типами полей при текущей `schemaVersion`.
  - `tests/unit/content-schema.test.ts` (новый) — 3 теста на `validateCampaignContent`:
    корректный конфиг проходит, неизвестный `configId` кидает читаемую ошибку, некорректный
    `AbilityConfig` (отрицательный `baseDamage`) кидает читаемую ошибку.
- Что реализовано: см. выше — вся ручная валидация заменена схемной, плюс новая проверка
  ссылочной целостности контента, которой раньше не существовало вовсе (`createLevelContent`
  раньше молча подставлял `health: 1` для неизвестного `configId` — теперь это explicit ошибка
  сборки/загрузки с понятным сообщением, как того требует план §4).
- Что намеренно не реализовано:
  - Схемы `AbilityConfig`/`EnemyConfig`/`CampaignLevelDefinition` в `src/content/schema.ts`
    структурные (строковые enum-поля типа `background`/`mechanic`/`effect`/`movement` проверяются
    как непустые строки, а не как конкретный перечисленный набор значений), потому что весь
    текущий контент (диалоги, названия уровней, мобы) относится к старому канону и будет полностью
    заменён по новому сценарию (см. `docs/AUDITS/CURRENT_STATE.md` §5, REPLACE). Жёстко зашивать
    сюда текущие строковые литералы значило бы создать техдолг, который придётся сразу
    переписывать при замене контента.
  - Внутренние подпапки `content/characters` и подпапки `core` (combat/entities/phase/...) не
    создавались — это отдельная задача (см. `docs/HANDOFFS/ARC-001.md`, раздел «Продолжение:
    целевая структура каталогов»).
  - Валидация `AppState`/переходов state machine схемой не добавлялась — вне scope, там уже есть
    типобезопасный `APP_TRANSITIONS`.
- Изменённые контракты: `parseSaveGame(value: unknown): SaveGame | null` — сигнатура и внешнее
  поведение не изменились для валидных/мигрируемых данных (проверено тестами), но данные с текущей
  `schemaVersion` и неверными типами полей теперь **отклоняются** (`null`), тогда как раньше они
  молча проходили с испорченными значениями внутри. Любой потребитель `parseSaveGame`, полагавшийся
  на «прощающее» поведение при неверных типах на `schemaVersion === 2`, должен обработать `null`
  (в кодовой базе такой потребитель не найден — `LocalStorageSaveRepository.load()` уже
  обрабатывает `null` из `parseSaveGame` как отсутствие сохранения).
- Проверки и результаты:
  - `npm run lint` — чисто.
  - `npm run typecheck` — чисто.
  - `npm run test` — 14 файлов / 35 тестов, все проходят (было 13/31, добавлено 4 новых теста).
  - `npm run build` — production build проходит, `validateCampaignContent` не бросает исключение
    на реальном контенте (подтверждает отсутствие ложных срабатываний на существующих 5 уровнях).
  - `npm run format:check` — чисто для всех изменённых файлов (2 оставшихся warning на `AGENTS.md`
    и `docs/ECLIPSE_PAWS_SCENARIO.md` существовали до этой задачи и не входят в её scope — не
    трогались).
- Ручная проверка: не применимо к UI/уровню — задача чисто инфраструктурная (валидация данных),
  визуальных изменений нет.
- Скриншоты/видео: не применимо.
- Известные ограничения:
  - `zod` был доступен транзитивно через `eslint-plugin-react-hooks` (`zod-validation-error`
    depends on него); теперь объявлен явной прямой зависимостью — устраняет риск скрытой
    поломки при будущем апдейте `eslint-plugin-react-hooks`, который мог бы убрать транзитивный
    `zod` из дерева.
  - `validateCampaignContent` запускается один раз при импорте модуля `campaign-levels.ts`
    (side-effect на module load) — это соответствует требованию плана «ошибки content-конфигураций
    выявляются при сборке или загрузке уровня», но означает, что ошибка валидации свалит импорт
    всего модуля контента, а не только конкретного уровня. Приемлемо для нынешнего размера
    контента (5 уровней), может потребовать точечной валидации per-level при росте до 7 уровней
    нового сценария.
- Риски для следующих задач: при замене контента под новый сценарий (7 уровней) новые данные
  автоматически пройдут через `validateCampaignContent` — это полезный safety net, но описание
  ошибок будет обрываться на первом валидируемом модуле, если контент будет собираться
  по частям (например, level-by-level lazy loading) — стоит учесть при замене контента под новый
  сценарий (Фазы 5+, `LV1-NNN`/`ART-NNN`, вне архитектурных `ARC-NNN` задач Фазы 1).
- Рекомендованный следующий task ID: `ARC-010` (Destroyable-контракт и полный cleanup для
  Phaser-систем в `prototype-scene.ts`) — не пересекается с текущей активной работой art-агента
  над `arena-decoration.ts`/`dream-environment-manifest.ts`, но стоит синхронизироваться перед
  стартом, так как обе задачи в итоге трогают `prototype-scene.ts`.
